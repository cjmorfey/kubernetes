# З kubeadm на RKE2

Це заміна дистрибутива і створення нового кластера. Etcd snapshot kubeadm не
є підтримуваним способом імпорту в RKE2. `setup` відмовляється працювати поверх
старого kubeadm/K3s чи стороннього RKE2 та нічого автоматично не видаляє.

Якщо машини ще чисті — одразу виконайте новий setup. Якщо кластер уже існує:

1. Збережіть декларативні маніфести, Helm values, CRD та залежності операторів.
   Перевірте сумісність API з вибраною версією Kubernetes. Не переносіть
   автоматично status, ServiceAccount tokens чи системний namespace kube-system.
2. Створіть перевірені резервні копії баз даних і PV. Окремо збережіть secrets,
   сертифікати та ключі шифрування згідно з вашою політикою. Snapshot etcd
   старого кластера потрібен для його відновлення, а не для імпорту в RKE2.
3. Найкраще — побудувати RKE2 на додаткових машинах, відновити дані, перевірити
   застосунки і перемкнути клієнтський DNS/LB після перевірки.
4. Якщо повторно використовуєте ті самі машини/IP, заплануйте downtime,
   перевірте offsite backups і можливість відновлення старого кластера.
   Після зупинки навантаження перевстановіть Ubuntu, зберігаючи поточні IP.
   Потім виконайте RKE2 setup. Автоматичного reset у новому сценарії немає.
5. Відновіть storage/operator-и, застосунки й дані в порядку їхніх залежностей.
   Перевірте ingress: у новому кластері використовується Traefik, а старі
   ingress-nginx annotation-и можуть вимагати переписування.
6. Перевірте записи/читання даних, доступи, DNS/TLS, мережеві політики,
   snapshots, recovery та моніторинг. Лише після цього завершуйте перенесення.

Оновіть Jenkins jobs, що прямо посилалися на master.yml, workers.yml,
preparation-steps-ubuntu.yml чи cleanup kubeadm: активний вхід тепер `./cluster`.
Архівні playbook-и залишені для історії й не запускаються з RKE2 pipeline.
